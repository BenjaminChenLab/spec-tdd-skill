# Changelog

All notable changes to the `spec-tdd` skill family are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),

## [1.8.1] - 2026-08-28

Dry-loop parameters retuned + `dryout` invocation flag (user-directed, design discussed and approved before implementation).

### Changed
- **Dry criterion simplified: ONE clean round stops the loop** — a round with zero BLOCKER/MAJOR findings (deduped re-finds excluded) is dry. Was 2 consecutive clean. Applies to both modes; the ONLY difference `dryout` makes is the cap.
- **`dryout` flag** (`/spec-tdd-adversarial dryout <feature>`): raises the dry-loop cap from 4 to 5 rounds; token stripped from the feature description; all other rules identical.
- **Cap-hit ask (both modes):** hitting the cap while fresh BLOCKER/MAJOR findings are still appearing now STOPS and ASKS the human whether to continue — a yes grants one more round, the ask repeats on further findings-rounds, a clean round or a decline ends it. The ask frames non-convergence as a signal with three named readings (superficial fixes manufacturing new issues / a lens category the list is missing / an oversized unit). Was: silent residual surfacing.
- PROTOCOL I8 synced; README adversarial row + version 1.8.1.

## [1.8.0] - 2026-08-28

**Terminal dry-loop audit** (user-directed, evidence-driven): a passed attack loop is not "done". Observed on a production `spec-tdd-adversarial` run (5 slices, overnight) — the in-run attacker loop passed, then a post-completion fresh-context audit landed **2 deployment-lens BLOCKERs** (a wrong migration-comment that would 500 every order in the deploy window; a runtime object with no creation path outside dev-profile controllers) and **2 test-strength MAJORs** the attacker hadn't constructed (a crash-window recovery path permanently dropped; a lifecycle state polled forever with its alert overwritten) — plus 8 minors (untested error handling surviving deletion, a missing mixed-scenario test, style violations). Half the findings were lenses the attacker structurally does not look through; half were attacker-lens findings it didn't reach. Both facts drive the design.

### Added
- **`spec-tdd-adversarial` Phase 3 step 5 — terminal dry-loop audit:** after the attack loop closes (either way), fresh read-only auditors, ONE lens per round, rotating — **test-strength** (wrong-but-green impls the attacker missed), **spec/plan fidelity** (clause-by-clause, incl. intermediate-failure/recovery promises), **deployment/ops** (migration windows old-code×new-schema and new-code×old-schema; environment-gated components; how EVERY runtime object comes to exist in EACH target environment; ops-doc claims), **production quality** (error handling, lifecycle convergence, dead code). **Dry-loop breaker:** a new round opens ONLY on a BLOCKER/MAJOR that is not a deduped re-find (same file:line / missing case / plan clause); STOP at **2 consecutive clean rounds or 4 total**; MINORs ride the report and never extend the loop; fixes needing a plan-level decision go to the human (I12). "No auditor finds anything" is never the bar — bounded dry is. Common-Mistakes (3 rows) + Red Flags added; step-6 surfacing carries the dry-loop rounds + residuals.
- **Grill deployment/rollout dimension** (`grill-spec-tdd` Phase 1 step 1): migration windows, environment-gated components, runtime-object existence per environment now an explicit grilled dimension; `adversarial-grill` Part A hunts un-grilled deployment windows under compatibility.
- **PROTOCOL I8 amendment:** the terminal dry-loop (rotating lenses, severity floor, dedup, 2-clean/4-cap) added to the adversarial independence invariant. Version 1.8.0.
- README: adversarial family-table row + mermaid attacker node carry the dry-loop; version 1.8.0.

### Design rationale (recorded in the baseline doc)
- NOT "fresh auditors until nobody finds anything": prove-a-negative, never terminates on a rich surface (the v1.2.1 breaker lesson), and without a severity floor it audits the auditors' taste — findings get manufactured to justify the round.
- Diminishing returns are steep (round 1 finds the bulk; round 2 the remainder; round 3+ marginal) — 2 consecutive clean rounds is the knee, 4 total is the zombie-loop cap.
- Lens rotation beats more same-lens rounds: the two BLOCKERs were invisible to the attacker's lens regardless of round count.
- Full record: [docs/specs/2026-08-28-dry-loop-baseline.md](docs/specs/2026-08-28-dry-loop-baseline.md).

## [1.7.1] - 2026-08-28

Pins an ambiguity surfaced in review (user-directed): **attacker/auditor identity across rounds.** The texts said "re-attack" and "one re-audit" without saying whether the same context continues — two opposite answers, both now explicit.

### Fixed
- **`spec-tdd-adversarial` + I8: each attack round is a FRESH dispatch** — never a continued conversation with the previous attacker. It has seen the orchestrator's strengthenings, so its context is contaminated and round 2 of the same context goes soft with ownership bias ("they fixed my findings"). The breaker's objective same-hole standard (the missing acceptance-test case, not a rephrased description) was already designed for cross-context comparison. Common-Mistakes row added.
- **`adversarial-grill-spec-tdd` + I16: the ONE re-audit continues the SAME auditor** — adoption checking (were the BLOCKERs really fixed, not papered over?) needs its memory of what it found; a fresh auditor burns the budget rediscovering known residuals. Principle stated in both skills: **attack wants freshness, adoption-check wants memory.**
- README and PROTOCOL version → 1.7.1.

## [1.6.0] - 2026-08-28

Two user-directed behavioral changes: the grill front-ends gate the **spec** (the grilled decisions) BEFORE any acceptance-test tokens are spent — the test is derived from the **final** (gate-approved) spec — and the family persists a **spec doc** by default whenever the spec isn't already a document, for later recall. The front-ends' gate is **blocking** (an unanswered gate parks the run — it never licenses proceeding on guesses); tiers run **after** the spec is final and add **no human gate of their own**.

### Changed
- **`grill-spec-tdd` — spec gate now precedes test authoring (gate-before-test).** Old order: write the test → RED → gate test + decisions. Failure modes closed: (a) test-authoring tokens burned on a spec the human redirects at the gate; (b) **amendment anchoring** — a gate amendment lands as a one-line test tweak instead of a re-derivation, so the test encodes the pre-gate draft, not what the human approved; (c) proceeding on guesses when the gate goes unanswered. New structure: **Phase 1** grill + ground + **spec gate** (decisions in plain language + routing choice + spec-doc ask as ONE go-ahead; amendments fold in → **FINAL SPEC**); **Phase 2** test derived from the final spec (every amendment included; a decision neither grill nor gate made → test-local mechanics are the agent's, material ones go back to the human — never silently into the test) + property tests + RED-purity; **Phase 3** route (unchanged semantics — the test is written and RED at handoff, so tiers still skip their Phase 1). **No-human fallback is a hard stop** (replaces the old defer-gate-to-PR): grill fully (self-directed), document + persist every decision, then PARK at the gate — no test tokens, no dispatch, until a human approves; "they'll answer eventually" is not an approval. Throwaway-tier gate-skip kept (pre-existing, stake-based; user-confirmed) — its spec-doc default still applies. Red flags + Common Mistakes updated (new: "writes the test before the gate", "amended decision → tweak the matching test line", silent test-writing decisions, doc-skipped-because-test-file-exists, skip/proceed-past-the-gate-because-no-one's-reachable).
- **`adversarial-grill-spec-tdd` — the grill-auditor splits into two dispatches around the gate.** **Part A** (decisions, dimension coverage, materiality stops, silent interpretations) stays **pre-gate** — its findings ride into the gate for the human to see. **Part B** (test strength: wrong-but-plausible final-spec readings, assertions beyond the spec, discriminating power, property-test tautologies, SPEC-DEFECT classes vs the real codebase, RED purity) moves **post-gate**: it attacks the test derived from the gate-approved final spec, still before any implementation tokens — post-gate by design, not omission (the test doesn't exist earlier under gate-before-test). New 4 phases: grill (no test) → Part A + reconcile (audit + one re-audit) → gate the spec → test from final spec + Part B + reconcile + route. Residual routing: Part A's at the gate; Part B's spec-level residuals surface to the human (follow-up ask — never decided silently), test-level residuals ride the tier handoff. No-dispatch disclosure split accordingly (Part A at the gate; Part B in the handoff). Multi-unit scope note updated (no writable spec yet → Part B has no subject, say so).
- **PROTOCOL.md**: **I12** amended (the grill front-ends' human gate approves the decision spec BEFORE the acceptance spec is authored; the acceptance spec is derived from the final decision spec — anchoring rationale stated; **the gate is blocking** — no approval parks the run: no test, no dispatch), **I16** amended (audit split: Part A pre-gate / Part B post-gate pre-dispatch, per-part audit + one re-audit bound, residual routing), A2/A14 When-columns updated, scope-table I16 label updated. Version 1.6.0.
- **`spec-tdd` multi-unit — the up-front checkpoint is gone; the plan is surfaced, not gated.** Tiers run after the spec is final (front-end gate or settled requirement) and add no spec gate of their own; the unit plan (A13) is HOW, not WHAT (I12). Write the unit plan + specs writable now, surface them at the start and in the batch summary — an interactive human can redirect on sight; the batch does not wait for an OK. Replaces the old ONE-human-OK checkpoint (and its subagent defer-to-report variant).

### Added
- **Spec-doc persistence, default ON — invariant I17 + artifact A15.** Entering a tier when the spec is **not a doc** — settled only in the conversation, nothing on disk — → prompt once whether to persist one; **default YES**: requirement verbatim + interpretation decisions + acceptance-spec path → `docs/specs/YYYY-MM-DD-<feature>.md` (project convention wins). A conversation is not durable recall (sessions get cleared/compacted). Skipped ONLY by an explicit user decline — an unanswered prompt is not a decline. The grill front-ends persist the **final decision spec** at the gate, bundled into the one gate ask. Wired into all four tiers: `spec-tdd` Phase 1 note, inheritance notes in `spec-tdd-coverage` / `spec-tdd-adversarial`, and `spec-tdd-lite` with the "session will be cleared — the doc is what survives" framing. Rationale: later recall (I10 SPEC-bucket re-opens, PR review, audits) must not depend on session memory; the executable acceptance spec does not replace it — tests are for running, docs are for recalling.
- README: mermaid grill path reordered (gate on the spec → test from the final spec), walkthrough reordered (grill → gate → test → route), family-table + front-ends prose + decision-tree + why-it-works updates, new spec-docs bullet, version 1.6.0.

### Fixed
- **README decision tree dead branch (1.5.0 defect, caught by release audit):** the Correctness-CRITICAL check exited to `spec-tdd-adversarial` BEFORE the fuzzy check, making `adversarial-grill-spec-tdd` unreachable — every fuzzy+critical requirement skipped the grill and both audits. ## [1.4.2] - 2026-08-21

Preventive hardening of the v1.4.1 SPEC-DEFECT clauses: two wording-level logic gaps found by adversarial review of the clauses themselves (one of them — the same categorical arity example also sitting in the implementer-side STOP clause — rated BLOCKER by the reviewer), fixed and pressure-tested. No misfire was observed in any single-shot test — the gaps were override burdens (an agent must reason *against* the categorical sentence to reach the right answer), not deterministic misclassification; the fixes close the categorical wording so the right answer no longer requires overriding the rule. Labeled preventive accordingly.

### Fixed
- **RED-purity breaking-change exception (I3).** "Any error about EXISTING symbols … is a defect in YOUR test" is categorical — but a feature that legitimately changes an existing symbol's signature produces exactly that error as a *good* RED. Added to every RED-purity site (spec-tdd/grill full sentence, lite/CM rows parenthetical, PROTOCOL I3): "unless the spec itself explicitly calls for changing that existing symbol (a breaking-change feature) — the error points at the shape the feature will create; the RED is good." Anchor is the requirement text, not the test author's belief.
- **Implementer-side false-SPEC-DEFECT guard (I15 list).** The STOP clause's own enumeration ("wrong constructor arity") invites a false report when the requirement itself changes the signature. Appended to both handoff templates, adversarial's inherited summary, lite's Phase-2 exception, and PROTOCOL I15: "an arity/signature error on a symbol the requirement itself explicitly changes is NOT a test defect — implement the change."
- **Sweep primary standard (I15).** "Every change the spec cannot trace" is an impossible primary net for behavioral specs (I2: WHAT, not HOW — most legitimate impl changes are untraceable) → false-positive flood → audit fatigue. Reordered in spec-tdd step 4, adversarial step 2, and lite's exit rule (PROTOCOL I15 mirrored): the subject is **changes to code this dispatch did not create** (new code is the feature's own shape), and the tell is change-level — **a change no production behavior needs, existing only to satisfy the acceptance test** (the test is not a production caller; note the rename case: the *change* has no beneficiary, even though the symbol has callers). "Logic beyond what the spec asks for" kept as a named shape.

### Verify-confirmed (7 fresh-subagent arms, temp-dir fixtures, real RED runs, real hashes)
- **S3 (breaking-change scenario — the GAP-1 trigger):** existing 2-arg `Shipment`, requirement adds a required 3rd ctor param. Orchestrator arm A (OLD clause) concluded correctly by requirement-over-clause (the override burden, observed); B (new clause, explicit requirement) invoked the exception cleanly; C (new clause, requirement *implying* rather than declaring the change) still held. Implementer arms D/D2 (OLD STOP clause, explicit and implied INTENT) — no false SPEC-DEFECT, GREEN, hash verified; E (new clause) GREEN, hash verified.
- **S4 (sweep scoping):** returned diff = 1 accommodation (ignored `legacy_mode` ctor param, only the acceptance test passes it) + legit pre-existing-file changes (gross→net, new spec'd methods) + a substantial new file. With the new wording: flagged ONLY the accommodation with full remediation (fix own test, re-hash, note, revert ctor), gave one-line not-flagged reasons for every other change, bounded effort — no false positives on new code. Claim deliberately narrowed: single-shot S4 proves non-misclassification, not fatigue resistance.

## [1.4.1] - 2026-08-21

SPEC-DEFECT discipline. The acceptance test itself can be defective, and an implementer under "immutable test + must go green" pressure will bend production to accommodate it instead of reporting. Observed on a production run (dtms-core LN system-RFI, `spec-tdd-coverage` flow): three accommodations — a 23-arg package-private compat constructor behind a 22-arg public ctor, public `post` renamed `postWithResponseType` across 3 call sites to dodge an ambiguous-overload compile error, LN resolution hoisted ahead of all workflowTypes to dodge an unnecessary strict-stubs stub — of which only one was passively reported. Root cause: the implementer's objective is "make the immutable test green"; when the test is defective, its only lever is production. Three clauses close it at three phases. Full incident record: [docs/specs/2026-08-21-spec-defect-baseline.md](docs/specs/2026-08-21-spec-defect-baseline.md).

### Added
- **RED-purity check** (I3 amendment) in every test-writing phase — `spec-tdd` Phase 1, `grill-spec-tdd` Phase 1 (before routing: the tier skips its Phase 1, so this is the only RED audit the test gets), `spec-tdd-lite` Phase 1, inherited notes in coverage/adversarial: scan the FULL error list, not the tail; every error must point at symbols the feature will create; errors about EXISTING symbols (wrong ctor arity, ambiguous overloads, unused imports) are a defect in YOUR test, fixed before dispatch. (The incident's 16-error RED list carried the ambiguity signal; only the tail 30 lines were read.)
- **SPEC-DEFECT STOP clause** in the Phase-2 handoff templates (`spec-tdd` and `spec-tdd-coverage` embedded; `spec-tdd-adversarial` carried by inheritance; `spec-tdd-lite` as the in-session self-audit variant): a defect in the TEST itself (wrong constructor arity, ambiguous overload matchers, unused stubs under strict stubs, assertions contradicting the spec) → STOP and report with evidence; production changes that exist solely to accommodate a test defect = a FAILED run; reporting a genuine SPEC-DEFECT is the correct outcome, not a failure to implement. RETURN amended: a SPEC-DEFECT stop returns the defect report instead of green output, and every run must return a **notable decisions** list (every deviation from the spec'd shape).
- **Phase-3 SPEC-DEFECT sweep** in orchestrator verification (`spec-tdd` step 4; coverage's checks; adversarial pre-attacker; lite exit rule): diff returned production changes against the spec/plan — any change the spec cannot trace, the general tell being a change whose only beneficiary is the acceptance test, is an accommodation → fix the orchestrator's own artifact (correct, re-hash, note the correction) and restore production to the spec'd shape. Scrutinize the implementer's notable-decisions list specifically for this failure mode.
- **PROTOCOL.md**: invariant **I15** (test-defect as a distinct failure mode: report-not-bend, symmetric incentives, the sweep, I4's escape hatch), I3 purity amendment, I4 escape-hatch extended to SPEC-DEFECT corrections, I10 TEST bucket names SPEC-DEFECT + SPEC-vs-TEST disambiguation (fixable from artifacts already held = TEST; requires deciding something the requirement doesn't decide = SPEC), scope-table I15 row, multi-unit per-unit note. Version 1.4.1.

### Changed

## [1.2.0] - 2026-08-12

The **prompt-discipline → protocol-discipline** release. Hardens the family's invariants from prose rules into enforceable procedures, and formalizes the method as a protocol. Each behavioral change was baseline-confirmed (RED — watched an agent fail under the old rule) and verify-confirmed (GREEN — watched it comply under the new one) via subagent pressure tests.

### Added
- **`PROTOCOL.md`** — the canonical spec of the method: artifacts (A1–A11) and invariants (I1–I12), with a drift-control statement (skills own *how* to enforce; PROTOCOL owns *what* the invariant is), a scope-per-tier matrix, and a "what the protocol does NOT guarantee" section. `spec-tdd` links to it.

- **Three-bucket failure routing (invariant I10).** Replaces the binary spec-flawed/impl-flawed with **SPEC** (re-open the requirement) / **TEST** (requirement right, executable spec weak or incomplete — strengthen it, do NOT re-open the requirement) / **IMPL** (re-delegate). - **Grill materiality stop (invariant I11).** `grill-spec-tdd` now stops when remaining questions can't materially change behavior / state / failure-semantics / data / security / compatibility / NFRs — bounds the grill by materiality, not exhaustion.
