# Payout action resolution — `payouts.py`

## Background

The payouts service evaluates each scheduled payout once per day during the
overnight batch. The batch needs a single, total decision per payout: what
should happen to it today. Historically this decision was scattered across
three systems (the scheduler, the KYC gate, and the treasury review queue),
which produced contradictory outcomes — a payout could be released by the
scheduler the same night the compliance queue thought it was frozen. This
module consolidates the decision into one pure function so the batch, the
audit log, and the operations dashboard all read the same answer.

The function is deliberately pure: no clock reads, no account lookups, no
I/O. Everything the decision depends on arrives as arguments, so the batch
supplies the current state and the module returns the disposition.

## API

```python
payout_action(scheduled_day, kyc_status, amount_cents) -> str
```

- `scheduled_day` — a three-letter uppercase weekday code, one of
  `'MON'`, `'TUE'`, `'WED'`, `'THU'`, `'FRI'`, `'SAT'`, `'SUN'`. This is the
  day the payout is scheduled to execute. The overnight batch runs on calendar
  days, so the weekday code fully determines whether the payout can execute
  today; there is no public-holiday calendar in scope and none should be
  invented.
- `kyc_status` — the account's verification state, one of `'VERIFIED'` or
  `'UNVERIFIED'`. Any other value is a contract violation: raise `ValueError`.
- `amount_cents` — the payout amount as a non-negative integer number of
  cents. A negative amount is a contract violation: raise `ValueError`.

Returns exactly one of the strings `'RELEASE'`, `'DEFER'`, `'HOLD'`,
`'ESCALATE'`. Any other return value is a defect. An invalid `scheduled_day`
(anything not in the seven codes above) is also a contract violation:
raise `ValueError`.

## Rules

**Scheduling.** A payout executes on its scheduled day when that day is a
business day. Business days are Monday through Friday. When the scheduled day
falls on a weekend, the payout cannot execute that day; the batch rolls it
forward to the next business day and the decision returned for today is
`'DEFER'`.

**Verification gate.** An account whose KYC state is `'UNVERIFIED'` may not
receive payouts. Funds for such an account are frozen where they stand: the
payout is marked `'HOLD'` and stays marked that way until the account passes
verification, at which point the payout re-enters the normal evaluation with
its original scheduled day.

**Escalation.** Payouts must never move large amounts without a human in the
loop. A payout is *large* when its amount exceeds the escalation threshold of
`100000` cents (the glossary pins the figure). Escalation is evaluated before
any scheduling consideration — a large payout must not silently roll forward
overnight; it surfaces for review now, and the decision returned is
`'ESCALATE'`.

## Glossary

- *business day* — Monday through Friday. Weekends (`'SAT'`, `'SUN'`) are
  never business days; there is no holiday calendar in scope.
- *escalation threshold* — `100000` cents. The figure is fixed for this
  module; it is not configurable.
- *large payout* — see Escalation.

## Acceptance criteria

1. The seven weekday codes are accepted; any other string raises `ValueError`.
2. `'UNVERIFIED'` accounts never produce a decision that moves money today.
3. Weekend payouts on business-day-only semantics produce `'DEFER'`.
4. Amounts above the escalation threshold on a verified account produce
   `'ESCALATE'`, including on weekends.
5. Negative amounts raise `ValueError`.
6. The function is pure: same inputs, same output, no global state.
