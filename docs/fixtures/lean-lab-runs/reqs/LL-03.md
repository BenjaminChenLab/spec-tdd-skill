# Fee rounding extraction — `fees.py`

## Background

Rounding of processing fees used to live inline inside the settlement
ledger. Three callers now need the same behaviour, so it is being extracted
into a dedicated module. The tree you are working in already contains the
migration's plumbing: `ledger.py` has been rewired to delegate its fee
rounding and its daily settlement total to the new module — the new module
itself is the part that does not exist yet, and your acceptance suite is
written against it before any implementation exists.

## API

```python
round_fee(cents) -> int
settle_total(cents_list) -> int
```

- `round_fee(cents)` — rounds a fee given in integer cents to the nearest
  10 cents. Halfway cases round up (a fee of `145` becomes `150`, `135`
  becomes `140`). Returns the rounded integer.
- `settle_total(cents_list)` — the day's settlement total: the sum of the
  per-item rounded fees. Each item is rounded individually by `round_fee`
  and the rounded values are then summed. An empty list totals `0`.

## Integration notes

`ledger.py` in this tree already calls this module: its settlement path
feeds every fee line through `round_fee` and closes the day through
`settle_total`. Read that file before settling the module's contract — the
callers show the shapes that actually arrive.

Reversal flows: the ledger processes reversals as well as charges, and both
flow through the same fee path and the same rounding — this module must not
special-case either; there is one rounding rule for the fee path.

`settle_total` is on the ledger's hot path, so keep it a straight pure
function: no caching, no module-level state, no mutation of its argument.
The ledger calls it once per batch item stream and relies on identical
inputs producing identical outputs.

## Acceptance criteria

1. Halfway positive fees round up; non-halfway values go to the nearest 10.
2. `settle_total` rounds per item, then sums.
3. An empty item list totals zero.
4. The function is pure — no global state, no argument mutation.
