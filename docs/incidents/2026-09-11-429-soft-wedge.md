# Incident 2026-09-11:429 soft-wedge——level-1 agent 卡死 5 小時、零通知、mid-run 指令無法送達

> 來源:dtms-core STP2 task loop 實戰(spec-tdd-task-loop,7+ 張卡經驗)。給 skill 優化 session:本文含完整證據、兩種失敗模式對照、已實證的 workaround、與 6 條 skill 端改進建議。

## TL;DR

5 小時用量池(glm-5.3 default pool)耗盡時,agent 有**兩種死法**:**hard-fail**(429 直接終止、有停止通知、可用 SendMessage 於重置後續跑——乾淨可恢復)與 **soft-wedge**(推理請求進入內部退避重試,agent 狀態恆為 `running`、**零通知**、transcript 停止更新、結果與佇列中的 mid-run 指令全部懸空)。本次 W11 level-1 屬後者:13:00 起 wedge 至 17:41 額度重置,佇列中 14:45 的「tier 降級、加快收斂」指令**永遠沒有送達**(SendMessage 只在下一輪工具回合投遞,而它再也沒有下一輪),agent 於是按舊的 coverage 深度標準多做數小時。偵測完全靠人工(transcript mtime + 背景 task 檔 mtime + 工作樹變化)。

## 環境

- Claude Code,三層 orchestration:主控(session,輕量 gate)→ level-1 spec-tdd orchestrator → nested implementer。
- 模型池:default pool(glm-5.3)有 5 小時滾動用量上限;sonnet/opus 為**不同池**(本次實證)。
- 同一工作樹,code 任務必須序列(整模組編譯互撞)——**wedge 的代價會沿關鍵路徑放大**:後續所有卡排隊等它。

## 根因

1. **額度耗盡的兩種表現非對稱**:hard-fail 會走正常終止流程(通知+可 resume);soft-wedge 是推理層的退避迴圈,harness 層面仍是「執行中」——**外部零訊號**。
2. **SendMessage 的投遞語意**是「下一輪工具回合」——對 wedged agent 等價於永不投遞。mid-run 政策(本次:tier 天花板降級)因此失效,agent 按過時的深度標準繼續燒額度,惡性循環(做越久→池越緊→越難醒)。
3. **skill 迴圈沒有 in-flight 監視**:gate 只在收案時跑,執行中沒有 heartbeat/時長檢查,wedge 只能靠人肉發現。

## 已實證的 workaround(本次用過、有效)

| 手法 | 適用 | 證據 |
| --- | --- | --- |
| **派工帶明確 `model` override**(sonnet=docs/MID、opus=TOP audit) | default 池耗盡期間仍需開工 | 14:17/15:12 兩顆 sonnet 於耗盡窗口正常完成 |
| **重置後 SendMessage 續跑**(context 保留) | hard-fail 的 agent | W10 於重置後 resume 成功(同日更早一次 429) |
| **人工 liveness 檢查**:tasks dir 內背景 task 檔 mtime + 工作樹 churn + agent 是否有訊息,對照 ListAgents 狀態 | 診斷 running-but-wedged | 本次確診 W11。⚠️ **`.output` transcript mtime 不可靠**——見下節「重置生效過程」的 17:53 證據(對已收案 agent 的 mtime=完成時間可参考;執行中 agent 的會長期凍結,連醒來後都不更新) |
| 排 one-shot cron 於預計重置後 +15~30min 做 保險介入 | 預期會有額度問題的日子 | 12:42 resume W10 成功;17:50 提前喚醒 W11 生效 |

## 給 skill 的改進建議(6 條,按價值排序)

1. **Watchdog 進 gate/迴圈**:orchestrator 記錄每張卡的 dispatch 時間;in-flight 超過門檻(如 90 分鐘無收案)→ 做 liveness 檢查。⚠️ 診斷訊號要用:**heartbeat 檔(見 #2)+ tasks dir 背景 task 檔 mtime + 工作樹 churn + agent 訊息**;**不要用 `.output` transcript mtime**——本次實證它對執行中 agent 長期凍結、醒來後也不更新(17:53 仍顯示 13:00 而 agent 已回報),只有對已收案 agent 才等於完成時間。寫進 spec-tdd-task-loop 的 orchestrator 責任清單。
2. **Heartbeat 慣例**(watchdog 的核心訊號):dispatch prompt 範本加一條——level-1 於每個 phase 邊界(每次 nested dispatch 前後)`touch .spec-tdd/<task>/HEARTBEAT`(或等價 echo)。母 session 便能分辨「在工作」與「wedge」,不靠猜、不靠不可靠的 mtime。
3. **mid-run 政策改走檔案通道**:tier 降級等指令**同時**寫進 level-1 每個 phase 邊界會重讀的檔案(如 task doc 開頭的 POLICY 區或 `.spec-tdd/POLICY-<task>.md`),SendMessage 僅當 best-effort 提醒。檔案對 wedged process 也能在醒來後第一時間生效——本次 14:45 的降級若走檔案,17:4x 醒來就會看到。
4. **首見 429 後的派工策略**:session 內任一 agent 出現 429 → 後續 dispatch 一律帶 `model` override(或暫停派工排到重置後)。明文化,不要靠臨場判斷。
5. **Wedge 後的恢復程序寫進 skill**:(a) 重置後 SendMessage nudge;(b) 仍不醒 → `TaskStop` + 重派一顆 fresh level-1,prompt 指示「盤點工作樹(git status)+ task doc + acceptance tests 現況後續做」——磁碟上的產物都活著,mid-flight 樹狀態可恢復,不必從零。
6. **序列成本提示**:task-loop 的說明要點明「同樹 code 任務序列,wedge = 整條佇列停擺」,讓 watchdog 有明確的正當性(不是過度監控)。

## 本次結局與「重置生效」的完整過程(值得單獨看)

重置**不是開關**,觀察到的恢復是分階段、有延遲的:

| 時間 | 事件 | 解讀 |
| --- | --- | --- |
| 17:41:22 | 額度池重置(429 訊息明載的時刻) | — |
| 17:46 | tasks dir 出現新的背景 task 檔寫入 | **子工作先恢復**——nested children 是獨立進程、有自己的退避迴圈,先解凍 |
| 17:50 | level-1 transcript mtime 仍凍在 13:00;主控送出喚醒+收斂 nudge(排隊) | 重置後 9 分鐘,parent 本體仍未醒 |
| ~17:51–53 | **level-1 醒來**:第一輪成功推理**一次投遞了全部兩則積壓訊息**(14:45 的 tier 降級+17:50 的喚醒),並立即回報完整狀態+收斂計畫 | 積壓訊息不會丟,按序在第一個成功回合全部送達 |
| 17:53 | `.output` mtime **仍顯示 13:00**(agent 明明已醒並回報) | transcript mtime 對執行中 agent 不可靠(收案時才可靠)——診斷方法的關鍵修正 |

**給 skill 的三個推論**:
1. 重置後的喚醒延遲實測 ≈10–12 分鐘(且子先於母)——「重置時刻≠可立刻要求收斂」,保險介入排在 reset+15min 以上是對的。
2. **積壓的 mid-run 指令不會丟失**——這是 soft-wedge 唯一的補償:file/message 雙通道裡,message 通道最終會在甦醒的第一輪補送。但別依賴它:指令若時效性強(如「別再做深活了」),晚 4 小時送達=沒送達。
3. 主控要意識到「醒來≠結束」:醒來只是開始消化積壓(nested 結果、訊息、收斂),距最終回報還有距離。

## 第三幕:zombie-wait——parent 健康地等一個已死的 child(18:46 確診)

重置生效後又拖了 ~1 小時仍無收案,主控深度活性檢查確診**第三種失敗模式**:

| 訊號 | 觀察(18:46) | 含義 |
| --- | --- | --- |
| 最後一次真實 gradle 測試 run | 15:15(test-results 凍結) | 3.5 小時無測試執行 |
| java/gradle 进程 | **零**(tasklist 查無) | 當下什麼都沒在跑 |
| 工作樹 | 24 項不變(production 最後寫入 15:10) | 無實質產出 |
| 背景 task 檔(b*) | 每隔幾分鐘冒新檔(18:12→15→42→46) | **有動作、零產出=thrashing 特徵** |

**機制**:nested implementer 於 ~15:15 死亡(死因可能是再度 429——child 與 parent 不同池不同命),**其死亡對 level-1 是靜默的**:parent 的 Agent 工具呼叫永遠不返回,parent 就永遠等。17:52 parent 回報「implementer 仍在背景跑」是**錯的**——它無從得知。背景 task 檔的間歇冒出是 parent 週期性 probe 的殘跡,不是工作。

**終局(18:47)**:主控 `TaskStop` 殺 level-1——被殺瞬間其積壓訊息送達:「實作者已派發並運行中,等待其完成」,坐實 zombie-wait。隨後 compile 探測:**BUILD FAILED 但全樹只有 1 個 error**(acceptance test 一處 checked exception 未宣告)——implementer 死在**差一行**的地方。`.spec-tdd/w11/` 證據完整(implementer-run.log、spec-integrity baseline、acceptance sha256 before/after)。

**恢復(18:49)**:重派 fresh agent(**不同模型池 opus**、帶盤點式恢復指令:讀 doc+scratch 證據+git status → 機械修完 → 單一合併 run → 標準回報)。結果見文末。

### 給 skill 的接續推論(接前三條)

4. **child 死亡對 parent 靜默**——nested Agent 呼叫不返回 ≠ child 在工作。skill 應要求:nested dispatch 時記下**時限預期**(「此 implementer 預期 X 分鐘」),parent 每次 probe 對照;超時即假設 child 已死、主動查證(工作樹/build 目錄 freshness),而非繼續等。
5. **thrashing 判定式**(watchdog 可直接用,不需讀 transcript):背景 task 檔在冒 **且** `build/test-results` 凍結 **且** 無 java 进程 = 空轉確診。
6. **kill 前先 SendMessage**:被殺 agent 的積壓訊息仍會送達(最後遺言)——免費拿到它的自我狀態認知(本次證明該認知可能是錯的,但診斷價值仍在)。

## 使用者定調(2026-09-11,Benjamin 原話):「要避免空轉。這功能比人做還慢」

這是對本 loop 的**根本性要求**,不是 nice-to-have:今天三種失敗模式疊加,一張卡 wall-clock ~6 小時、其中 ~5 小時零產出——比人手做還慢。skill 的改進必須把「**零產出時長**」當第一級指標:

- **每張卡有 wall-clock 預算**(依 S/M/L 給上限,如 S=30min/M=60min/L=120min),watchdog 每 15 分鐘檢查「自上次**實質產出**(工作樹 diff 或測試結果變化,非背景檔)以來的時長」;超過 15 分鐘零實質產出→介入,超過預算→終止重派。**沒有「再等等」**。
- **空轉的定價要寫進 skill 文件**:同樹序列下,一張卡空轉=整條佇列停擺——watchdog 不是過度監控,是常態成本。
- 若環境(harness)做不到可靠的心跳/死亡通知,** 寧可降級為「主控親跑最終驗證」的收尾模式**(本次恢復所探用的路徑),也不要讓一條卡無限等。

## 給優化 session 的建議清單(按優先序,源自本次全案)

1. **Anti-idle watchdog(最高)**:上面「使用者定調」段的三條——預算+實質產出檢查+終止重派,做成 orchestrator 端的常規步驟(排程檢查,非人肉)。
2. **Heartbeat 檔慣例**:dispatch 範本加 `touch .spec-tdd/<task>/HEARTBEAT`(每 phase 邊界);watchdog 的主訊號(取代不可靠的 transcript mtime)。
3. **429 應變**:session 內首見 429 → 後續 dispatch 帶 model override(不同池,實證有效)或停派到重置後;hard-fail 與 soft-wedge 兩種形態的處置劇本寫死。
4. **Mid-run 政策走檔案**:tier 變更等指令寫進 agent 每個 phase 邊界會重讀的檔案;SendMessage 僅 best-effory(對 wedged agent 永不投遞,但甦醒後會補送——時效性強者不可依賴)。
5. **Nested 時限預期**:parent 記錄每個 child 的預期時長,超時主動查證(child 死亡靜默)。
6. **恢復劇本標準化**:kill → 盤點(樹+scratch+doc)→ 不同池 fresh agent 機械收尾 → 主控親跑單一合併驗證(備援)。本次實測可行,寫成 runbook。

## 恢復結果

**恢復 agent(opus、不同池)耗時 ~5.4 分鐘**完成整個收尾:讀盤點→一行 test-fix(throws 子句,前任 log 已處方)→單一合併 run 452/0/0→標準回報。零 production 改動——前任實作本來就完整,只差一行 compile。

**對照數字(給優化 session 的最強論據)**:事故浪費牆鐘 ~5.5 小時(13:00 wedge→18:47 kill),恢復只花 5 分鐘。**早期終止+重派遠比等待便宜**——watchdog 的介入門檻應該激进(15 分鐘零實質產出即可動手),「再等等」在本案的期望值是負的。
