# Incident 2026-09-11: 429 soft-wedge — a level-1 agent wedged for 5 hours, zero notifications, mid-run instructions undeliverable

> Source: dtms-core STP2 task-loop field run (spec-tdd-task-loop, 7+ cards of experience). For the skill-optimization session: this document carries the complete evidence, a comparison of the two failure modes, field-proven workarounds, and 6 skill-side improvement recommendations.

## TL;DR

When the 5-hour usage pool (glm-5.3 default pool) ran out, the agent had **two ways to die**: **hard-fail** (429 terminates directly, with a stop notification, resumable via SendMessage after reset — cleanly recoverable) and **soft-wedge** (the inference request enters an internal backoff-retry loop; the agent's state stays `running` with **zero notifications**, the transcript stops updating, and results plus any queued mid-run instructions all hang). This day's W11 level-1 was the latter: wedged from 13:00 until the 17:41 quota reset; the queued 14:45 instruction "downgrade the tier, converge faster" **was never delivered** (SendMessage only delivers at the next tool round, and there never was a next one), so the agent kept working for extra hours to the old coverage depth standard. Detection was entirely manual (transcript mtime + background task-file mtime + working-tree changes).

## Environment

- Claude Code, three-layer orchestration: main controller (session, lightweight gate) → level-1 spec-tdd orchestrator → nested implementer.
- Model pools: the default pool (glm-5.3) has a 5-hour rolling usage cap; sonnet/opus are **different pools** (field-proven this day).
- One working tree; code tasks must serialize (whole-module builds collide) — **the wedge's cost amplifies along the critical path**: all subsequent cards queue behind it.

## Root cause

1. **The two faces of quota exhaustion are asymmetric**: hard-fail goes through the normal termination flow (notification + resumable); soft-wedge is an inference-layer backoff loop that still reads as "running" at the harness layer — **zero external signal**.
2. **SendMessage's delivery semantics** are "the next tool round" — for a wedged agent that means never. The mid-run policy (here: a tier-ceiling downgrade) is thereby voided; the agent keeps burning quota on an outdated depth standard, a vicious circle (the longer it works → the tighter the pool → the harder to wake).
3. **The skill loop has no in-flight monitoring**: the gate only runs at close; nothing during execution — no heartbeat, no duration check; a wedge can only be found by hand.

## Skill-side improvement recommendations (6, ranked by value)

1. **Watchdog into the gate/loop**: the orchestrator records each card's dispatch time; in-flight past a threshold (e.g. 90 minutes without closing) → run a liveness check. ⚠️ The diagnostic signals to use: **heartbeat file (see #2) + tasks-dir background task-file mtime + working-tree churn + agent messages**; **do not use `.output` transcript mtime** — this day proved it freezes long-term for running agents and doesn't update after waking (at 17:53 it still showed 13:00 while the agent had already reported); only for closed agents does it equal the completion time. Write this into spec-tdd-task-loop's orchestrator responsibility list.
2. **Heartbeat convention** (the watchdog's core signal): add one item to the dispatch prompt template — level-1 `touch .spec-tdd/<task>/HEARTBEAT` (or an equivalent echo) at every phase boundary (before/after each nested dispatch). The parent session can then tell "working" from "wedged" without guessing and without unreliable mtimes.
3. **Mid-run policy moves to a file channel**: instructions like tier downgrades are **also** written into a file level-1 re-reads at every phase boundary (e.g. a POLICY section at the head of the task doc or `.spec-tdd/POLICY-<task>.md`), with SendMessage as a best-effort reminder only. A file takes effect the moment a wedged process wakes — if the 14:45 downgrade had gone by file, it would have been seen the moment it woke in the 17:4x window.
4. **Post-first-429 dispatch policy**: any agent in the session hits a 429 → every subsequent dispatch carries an explicit `model` override (or dispatching pauses until after reset). Codify it; don't rely on in-the-moment judgment.
5. **Write the post-wedge recovery procedure into the skill**: (a) post-reset SendMessage nudge; (b) still not waking → `TaskStop` + re-dispatch a fresh level-1 whose prompt instructs "inventory the working tree (git status) + task doc + acceptance tests, then continue from where things stand" — the artifacts on disk are all alive; mid-flight tree state is recoverable; no need to start from zero.
6. **State the serial cost**: task-loop's docs must spell out "same-tree code tasks serialize; a wedge = the whole queue stalled", giving the watchdog clear legitimacy (not over-monitoring).

## This day's ending and the full "how the reset took effect" process (worth reading on its own)

The reset **is not a switch**; the observed recovery came in stages, with delays:

| Time | Event | Reading |
| --- | --- | --- |
| 17:41:22 | Quota pool resets (the moment stated in the 429 message) | — |
| 17:46 | New background task-file writes appear in the tasks dir | **child work recovers first** — nested children are independent processes with their own backoff loops, thawing first |
| 17:50 | level-1 transcript mtime still frozen at 13:00; the controller sends a wake + convergence nudge (queued) | 9 minutes after reset, the parent body still hasn't woken |
| ~17:51–53 | **level-1 wakes**: the first successful inference round delivers **both backlogged messages at once** (the 14:45 tier downgrade + the 17:50 wake) and immediately reports full status + a convergence plan | backlogged messages are not lost; all delivered in order at the first successful round |
| 17:53 | `.output` mtime **still shows 13:00** (the agent is clearly awake and has reported) | transcript mtime is unreliable for running agents (only reliable at close) — a key correction to the diagnostic method |

**Three inferences for the skill**:
1. Measured post-reset wake delay ≈10–12 minutes (and children before the parent) — "the reset moment ≠ you can demand convergence immediately"; scheduling the insurance intervention at reset+15 min or later is correct.
2. **Backlogged mid-run instructions are not lost** — soft-wedge's only compensation: in the dual file/message channels, the message channel eventually redelivers on the first waking round. But don't rely on it: for strongly time-critical instructions (like "stop doing deep work"), delivered 4 hours late = not delivered.
3. The controller must realize "waking ≠ finished": waking only begins the backlog digestion (nested results, messages, convergence); the final report is still some distance away.

## Act three: zombie-wait — a healthy parent waiting on a dead child (diagnosed 18:46)

After the reset took effect, another ~1 hour dragged by with no closure; the controller's deep liveness check diagnosed a **third failure mode**:

| Signal | Observation (18:46) | Meaning |
| --- | --- | --- |
| Last real gradle test run | 15:15 (test-results frozen) | 3.5 hours without a test execution |
| java/gradle processes | **zero** (tasklist finds none) | nothing running at all at that moment |
| Working tree | 24 items unchanged (last production write 15:10) | no real output |
| Background task files (b*) | a new file every few minutes (18:12→15→42→46) | **activity with zero output = a thrashing signature** |

**Mechanism**: the nested implementer died at ~15:15 (cause possibly another 429 — child and parent on different pools, different fates), and **its death was silent to level-1**: the parent's Agent tool call never returns, so the parent waits forever. The 17:52 parent report "the implementer is still running in the background" was **wrong** — it had no way to know. The intermittent appearance of background task files is residue of the parent's periodic probing, not work.

**Endgame (18:47)**: the controller `TaskStop`s level-1 — at the instant of the kill its backlogged message delivers: "the implementer has been dispatched and is running; waiting for it to finish", confirming the zombie-wait. A subsequent compile probe: **BUILD FAILED with exactly 1 error across the whole tree** (an undeclared checked exception in one spot in the acceptance test) — the implementer died **one line short**. The `.spec-tdd/w11/` evidence is complete (implementer-run.log, spec-integrity baseline, acceptance sha256 before/after).

**Recovery (18:49)**: re-dispatch a fresh agent (**a different model pool, opus**, with an inventory-style recovery instruction: read the doc + scratch evidence + git status → mechanically finish → one merged run → standard report). Result at the end of this document.

### Follow-up inferences for the skill (continuing the first three)

4. **A child's death is silent to the parent** — a nested Agent call not returning ≠ the child working. The skill should require: at nested dispatch, record a **time-limit expectation** ("this implementer is expected to take X minutes"); the parent checks against it at every probe; on timeout, assume the child is dead and actively verify (working-tree / build-dir freshness) instead of waiting on.
5. **The thrashing verdict formula** (directly usable by a watchdog, no transcript read needed): background task files appearing **AND** `build/test-results` frozen **AND** no java processes = idling confirmed.
6. **SendMessage before the kill**: a killed agent's backlogged messages still deliver (last words) — free intel on its self-state understanding (this day proved that understanding can be wrong, but the diagnostic value stands).

## The user's framing (2026-09-11, Benjamin's words, translated from the original): "Idling must be avoided. This is slower than a human doing it."

This is a **fundamental requirement** on this loop, not a nice-to-have: today's three stacked failure modes made one card ~6 h wall-clock with ~5 h zero output — slower than doing it by hand. Skill improvements must treat **zero-output duration** as the first-class metric:

- **Every card gets a wall-clock budget** (caps by S/M/L, e.g. S=30min/M=60min/L=120min); the watchdog checks every 15 minutes "time since the last **real output** (working-tree diff or test-result changes, not background files)"; over 15 minutes of zero real output → intervene; over budget → terminate and re-dispatch. **No "wait a bit longer."**
- **Price the idling into the skill docs**: under same-tree serialization, one card idling = the whole queue stalled — the watchdog is not over-monitoring, it is a standing cost.
- If the environment (harness) cannot deliver reliable heartbeats / death notifications, **degrade to a closing mode of "the controller personally runs the final verification"** (the path this day's recovery took) rather than letting a card wait indefinitely.

## Recommendation list for the optimization session (priority order, from this whole case)

1. **Anti-idle watchdog (highest)**: the three items in the "user's framing" section above — budgets + real-output checks + terminate-and-redispatch — as a routine orchestrator-side step (scheduled checks, not by hand).
2. **Heartbeat file convention**: add `touch .spec-tdd/<task>/HEARTBEAT` to the dispatch template (every phase boundary); the watchdog's primary signal (replacing unreliable transcript mtimes).
3. **429 contingency**: first 429 in the session → subsequent dispatches carry a model override (different pool, field-proven) or pause until after reset; write down hard the disposal playbooks for both shapes, hard-fail and soft-wedge.
4. **Mid-run policy via file**: instructions like tier changes written into a file the agent re-reads at every phase boundary; SendMessage is best-effort only (never delivered to a wedged agent, but redelivered on waking — strongly time-critical instructions must not rely on it).
5. **Nested time-limit expectations**: the parent records each child's expected duration and actively verifies on timeout (child death is silent).
6. **Standardize the recovery playbook**: kill → inventory (tree + scratch + doc) → a different-pool fresh agent mechanically closes out → the controller personally runs one merged verification (the backstop). Field-tested workable this day; write it up as a runbook.

## Recovery outcome

**The recovery agent (opus, different pool) took ~5.4 minutes** to finish the whole close-out: read the inventory → a one-line test fix (a throws clause, already prescribed in the predecessor's log) → one merged run 452/0/0 → the standard report. Zero production changes — the predecessor's implementation was already complete, one compile line short.

**The contrast numbers (the strongest argument for the optimization session)**: the incident wasted ~5.5 h of wall-clock (13:00 wedge → 18:47 kill); the recovery took 5 minutes. **Early termination + re-dispatch is far cheaper than waiting** — the watchdog's intervention threshold should be aggressive (act at 15 minutes of zero real output); "wait a bit longer" had negative expected value in this case.
